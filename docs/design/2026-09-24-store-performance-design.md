# Store Performance Cockpit: design
- **Architecture:** [docs/architecture.md](../architecture.md)

## 1. Goal

Build a governed analytics product for the store network of a discount grocery retailer. It
covers the full lifecycle of an enterprise Power BI solution on Microsoft Fabric:
requirements, design, data preparation, a secured semantic model, usability-tested reports
and controlled deployment. Sales data is real (Corporación Favorita, Kaggle). ERP data that
the public dataset lacks is synthetic and labelled as such.

## 2. Users and their questions

| Persona | Device and rhythm | Must answer in under a minute |
|---|---|---|
| Store manager | Phone, daily | How did my store do yesterday vs. target? Which fresh items look out of stock? |
| Regional manager | Desktop, weekly | Which of my stores are behind on like-for-like sales, and is it fewer shoppers or smaller baskets? |
| Category manager (fresh and promotions) | Desktop, weekly | Which promotions lifted sales and which only shifted them? Where are we losing fresh sales? |
| Head office | Desktop, monthly | Is the network on plan, and which region needs attention? |

## 3. Scope

### 3.1 Report

One report, published through one Power BI app:

1. **Network overview**: sales vs. target, like-for-like (LFL) growth, receipts (footfall) and basket value, by region, with prior-year comparison.
2. **Store performance**: store ranking by LFL growth; LFL growth split into footfall and basket; weekday and rain patterns; drill-through to a store detail page.
3. **Fresh and availability**: fresh (perishable) share of sales, stock-out risk list, estimated lost units and sales.
4. **Promotions**: promotion uplift, post-promotion dip, promotion share; margin (Commercial role only).
5. **Phone layout**: the store manager's daily view.

### 3.2 Success criteria

- Every requirement in `docs/requirements.md` links to visible evidence in the README.
- The Best Practice Analyzer (BPA) check reports zero errors and CI is green on `main`.
- RLS and OLS are verified with four test users, one per persona, with screenshots in `docs/security.md`.
- Every visual's query runs in under 500 ms on a warm cache on full data, with before/after evidence in `docs/performance.md`.
- A usability test with 5 participants reaches at least 80% task success on v2, and the SUS score is reported (target 70 or more).
- The model opens offline in Power BI Desktop on the sample data.

### 3.3 Out of scope

Forecasting and machine learning, Databricks, real-time data, paginated reports, publish to
web, sensitivity labels.

## 4. Data

### 4.1 Sources

| Source | Content | Notes |
|---|---|---|
| Favorita (Kaggle competition files) | Daily unit sales per store and item (~125M rows, 2013-01 to 2017-08), promotion flag, daily receipts per store, stores, items, holidays | Downloaded by script after accepting the competition rules. Raw files are never committed. |
| Azure SQL `retail-erp` | Region mapping, store profile, item price and cost, monthly targets, weekday weights, user → store access | Synthetic, generated by a seeded script (reproducible) |
| Open-Meteo archive API | Daily precipitation and maximum temperature per store city | Free for non-commercial use; attribution (CC BY 4.0) shown in the README and report |

### 4.2 Synthetic data rules

The Favorita data has units only: no prices, costs, targets or organisation structure. A
seeded generator creates these, and every synthetic column is listed in `docs/requirements.md`:

- **Unit price**: drawn per item from a family-specific range. **Unit cost** = price × (1 − family margin rate).
- **Monthly target** per store: the store's prior-year sales value for the same month × (1 + growth). Growth is drawn per store and month from a normal distribution (mean 3%, sd 2%). Targets exist from the first month that has a full prior-year month.
- **Weekday weights** per store: each weekday's share of the store's sales value over the store's full history.
- **Regions**: Pichincha → *Quito*; Guayas → *Guayaquil*; the other Andean provinces → *Sierra*; the remaining coastal and Amazon provinces → *Costa & Oriente*. The seed fails if any store's state is unmapped.
- **Selling area** per store: drawn from a store-type-specific range.
- **Opening date** is not synthetic: it is the store's first day with receipts (full history).

### 4.3 Sample dataset

Six stores (three in *Quito*, three in *Guayaquil*) from 2016-01-01 onward, built by the same
pipeline with a `--sample` flag. It feeds the Dev workspace, Power BI Desktop development and
the offline demo. Two regions are included so region-level RLS can be shown on the sample.

## 5. Architecture decisions

| # | Decision | Reason |
|---|---|---|
| D1 | Hybrid lakehouse: large-file preparation runs locally in DuckDB SQL; small external sources run through Dataflow Gen2 | Heavy processing is free and doesn't consume trial capacity. The SQL can later move to a Fabric notebook or Databricks. |
| D2 | The semantic model reads only lakehouse tables | One way into the model; any storage mode can read plain Delta tables |
| D3 | Import storage mode by default; the Prod mode is decided by a benchmark (Import vs. composite with aggregations vs. Direct Lake) | Choosing aggregations and Direct Lake appropriately needs measured evidence. Direct Lake has no user-defined aggregations and needs Fabric capacity. |
| D4 | Targets stored monthly and allocated to days by a T-SQL view using weekday weights | Monthly is the realistic ERP grain; daily targets let "yesterday vs. target" work |
| D5 | Dynamic RLS through an unrelated access table read with `USERPRINCIPALNAME()`, plus OLS on unit cost | Scales to any number of stores without new roles and avoids bi-directional relationships |
| D6 | Sales value = `SUMX` over the Item table, with price stored once on Item | Iterates about 4,000 items instead of about 100M fact rows; tested in the benchmark against a precomputed column |
| D7 | The sample lakehouse feeds Dev and Desktop; a deployment rule switches Test and Prod to full data | Fast development, a small offline demo, and a meaningful deployment rule |
| D8 | PBIP (TMDL model, PBIR report) in Git, with the BPA check in CI | Reviewable diffs and an enforced quality gate |
| D9 | Separate data workspace (`Retail Data`) and content workspaces (`Retail BI` Dev/Test/Prod) | The data layer is shared; only content is promoted |
| D10 | Stock-out risk and promotion baselines are computed upstream in SQL, not in DAX | Heavy window logic belongs in data preparation; DAX stays simple and fast |

Each decision gets a short decision record in `docs/decisions/` during implementation.

## 6. Local pipeline

- **Stages**: download → bronze (raw CSV to typed Parquet) → silver (cleaned: returns separated, missing promotion flags marked unknown, keys typed) → gold (the table contract in `docs/architecture.md`) → tests → upload.
- **Promotion baseline** (on promotion and post-promotion rows only; null elsewhere, which keeps the column small):
  - Definition: the average daily units for the same store and item over the trading days (receipts > 0) in the 28 days before the row's date.
  - Rules: days without a sales row count as zero; days on promotion are excluded.
  - Known approximation: Favorita has no promotion flag on zero-sale days, so those days are treated as non-promotion days.
  - Known approximation: Post-promotion days with zero sales have no row, so Post-promo Dip % is biased toward zero.
- **Post-promotion window**: the 7 days after a store-item promotion ends, excluding days that are themselves on promotion.
- **Stock-out risk** (2016-01-01 onward), flagged when all of these hold:
  - the store traded a normal day: receipts are at least half its average over the previous 28 days (partial trading days are not evidence);
  - the item has no sales row;
  - the item's average daily units over the previous 28 trading days (λ, with missing sales rows counted as zero) is at least 3, so a zero-sale day has a Poisson probability of at most 5%;
  - the item sells again at the same store within the next 28 days, which excludes delistings.
  - `ExpectedUnits` = λ.
- **Upload**: gold tables are written as Delta and uploaded to the lakehouse `Tables/` area, one atomic overwrite per table, and only if all tests pass.

## 7. ERP database (Azure SQL)

- **Schema `erp` tables**:
  - `region`, `state_region`
  - `store_profile` (selling area)
  - `item_price` (unit price, unit cost)
  - `sales_target_month`, `weekday_weight`
  - `city_geo` (latitude and longitude, from the Open-Meteo geocoding API)
  - `weather_daily` (rain and maximum temperature per city and day, from the Open-Meteo archive API)
  - `user_access` (user principal name, store number)
- **View `erp.v_sales_target_day`**: allocates each monthly target to the store's planned open days (25 Dec and 1 Jan are planned closures) in proportion to its weekday weights; daily values sum back exactly to the monthly target (the last open day absorbs rounding).
- **Constraints and data**: primary keys, foreign keys and CHECK constraints (price > cost > 0, weights > 0). A single idempotent seed script creates and loads everything.

## 8. Dataflow Gen2 (`df_erp_weather`)

- **Joins onto the staged tables**:
  - `stg_store` + `erp.store_profile` + region → `dim_store`
  - `stg_item` + `erp.item_price` → `dim_item`
  - `stg_store_day` + `erp.v_sales_target_day` + weather → `fact_store_day`, driven by the union of store-days with receipts and store-days with a daily target, so a closed day keeps its target
- **Other outputs**: `user_access` → lakehouse.
- **Weather** is joined from `erp.weather_daily`. The local pipeline (`retail_pipeline weather`) makes one archive API call per city for the full date range, 15 seconds apart, and writes nothing unless every city succeeds; `erp-load` then loads it and a SQL test checks that every store city has weather.
  - Changed during the build: Dataflow Gen2 on the F2 capacity failed every `Web.Contents` call to the API with a generic evaluation error, so the API call moved to the pipeline.

## 9. Semantic model: `Store Performance`

### 9.1 Tables and relationships

- **Tables**: Sales, Store Day, Stock-out Risk (facts); Date, Store, Item (dimensions); User Access (hidden, unrelated); Time Calc (calculation group); Metric (field parameter).
- **Relationships**: one-to-many, single direction, integer keys. Date is marked as the date table and auto date/time is off.
- **Columns**: keys and technical columns are hidden; every column has a data type, summarization and category set deliberately.

### 9.2 Key measures

| Measure | Definition |
|---|---|
| Units | `SUM('Sales'[Unit Sales])` |
| Sales Value | `SUMX('Item', [Units] * 'Item'[Unit Price])` |
| Cost Value | `SUMX('Item', [Units] * 'Item'[Unit Cost])`; unavailable to Store operations (OLS) |
| Gross Margin % | (Sales Value − Cost Value) ÷ Sales Value |
| Receipts | `SUM('Store Day'[Receipt Count])` |
| Basket Value | Sales Value ÷ Receipts |
| Target | `SUM('Store Day'[Target Value])` |
| Sales vs Target % | (Sales Value − Target) ÷ Target |
| LFL Sales, LFL Sales PY, LFL Growth % | Sales for stores whose opening date is at least 12 months before the start of the selected period; growth vs. the same period last year |
| LFL Footfall Growth %, LFL Basket Growth % | Same store set; (1 + sales growth) = (1 + footfall growth) × (1 + basket growth) |
| Fresh Share % | Sales Value of perishable items ÷ Sales Value of all items |
| Promo Uplift % | (Units − Baseline Units) ÷ Baseline Units on promotion rows |
| Post-promo Dip % | (Units − Baseline Units) ÷ Baseline Units in post-promotion windows |
| Stock-out Risk Items | Distinct flagged store-item pairs in the period |
| Est. Lost Units, Est. Lost Sales | Sum of expected units on flagged days; valued at unit price |

The calculation group `Time Calc` has these items: Actual, MTD, YTD, PY, PY YTD, YoY Δ, YoY %,
with dynamic format strings for percentage items. The field parameter `Metric` switches trend
charts between Sales Value, Units, Receipts and Basket Value.

**Conventions**: every measure has a description, a display folder and a format string. The
KPI glossary (`docs/kpi-glossary.md`) holds the business definition next to the DAX.

## 10. Security

| Role | Row filter | OLS | Members |
|---|---|---|---|
| Store operations | `'Store'[StoreKey]` in the user's rows of User Access | `Item[Unit Cost]` = none | Store and regional managers |
| Commercial | None | None | Category managers, head office |

- **App audiences** control reports. Audiences show or hide whole items, not pages, so each page is its own report on the shared model:
  - Store managers: store performance, fresh and availability, store today (phone layout).
  - Regional managers: network overview, store performance, fresh and availability.
  - Category managers: network overview, fresh and availability, promotions.
  - Head office: all reports.
- **Test users** (created in the tenant, app access only):
  - one store manager (a sample store)
  - one regional manager (a sample region)
  - one category manager
  - one head-office user
- **Test matrix**: expected stores and fields per user, checked in Desktop ("View as") and in the Service.

## 11. Report and UX

1. **Requirements**:
   - personas and about 10 user stories with acceptance criteria (`docs/requirements.md`)
   - the KPI glossary
2. **Design in Figma**:
   - wireframes;
   - then a small design system: colour tokens (colour-blind safe, contrast-checked), type scale, 8-px grid, KPI card, chart styles;
   - then high-fidelity 1280 × 720 pages and the phone layout.
   - Exports: a Power BI theme JSON in `design/`.
3. **Build v1** from the design.
4. **Usability test**:
   - 5 participants, 5 think-aloud tasks each;
   - measures: task success, time on task, SUS;
   - protocol and results in `docs/usability/`;
   - findings drive a v2 change log.
5. **Accessibility**:
   - text contrast at least 4.5:1, non-text at least 3:1;
   - colour is never the only signal;
   - alt text on every visual;
   - logical tab order.
6. **Chart rules**:
   - no pie or donut charts for non-additive measures;
   - titles state the question the visual answers;
   - units and periods are always labelled.

## 12. Performance

- **Budget**: under 500 ms per visual query, warm cache, on full data in the Test stage.
- **Benchmark queries**: 6 DAX queries taken from the heaviest visuals, run in DAX Studio. Each is run 5 times cold and 5 times warm; results report the median, the formula-engine vs. storage-engine split, and the number of storage-engine queries. Model size comes from VertiPaq Analyzer.
- **Variants**:
  - V1: Import.
  - V2: composite model, with the Sales detail in DirectQuery to the SQL analytics endpoint plus an imported store × family × day aggregation table.
  - V3: Direct Lake on OneLake.
- **Decision**: the fastest variant that meets the budget and the operating constraints goes to Prod, recorded in a decision record with the numbers.
- **Before-benchmark hygiene**: remove unused columns, use integer keys, split date and time, avoid high-cardinality text in fact tables, and use variables and dimension-level iteration in DAX.

## 13. Testing

| Layer | Checks | Where |
|---|---|---|
| Pipeline | Unique keys, not-null, every fact key exists in its dimension, raw vs. gold totals reconcile per year, accepted values | pytest + DuckDB: CI on a small synthetic fixture shaped like the Favorita files (no Kaggle data committed); locally on full data |
| ERP | Constraints; daily targets sum exactly to monthly targets | SQL test script against Azure SQL |
| Model | BPA rules (Microsoft's standard set plus project rules); DAX totals equal SQL endpoint totals per year and region | BPA in CI; the totals check before every promotion to Prod |
| Security | Four-user RLS/OLS test matrix | Desktop and Service |
| Report | Accessibility and design checklist; usability test | Manual |
| Performance | Benchmark against the budget | DAX Studio |

## 14. Error handling and operations

- **Pipeline**: explicit schemas, so a source schema change fails the run. Re-runs are safe because each table is overwritten. Nothing uploads unless every test passes, and row counts are reported for every gold table.
- **Weather**: a failed API call stops `retail_pipeline weather` before anything is written; `erp/tests.sql` fails the load if a store city has no weather.
- **Refresh**: the data pipeline refreshes the dataflow, then the semantic model. Refresh-failure notifications go to the owner's personal email address.
- **Promotion to Prod**: happens only after the Test totals check passes.

## 17. Risks

| Risk | Mitigation |
|---|---|
| The Fabric trial was refused for this tenant (happened) | Paid F2 capacity, paused when idle ([ADR-011](../decisions/ADR-011-paid-f2-capacity.md)); screenshots captured while it runs; the Import model on sample data opens offline |
| Laptop memory with ~125M rows | DuckDB reads Parquet in a streaming fashion and spills to disk; stock-out spine limited to 2016 onward; the sample is used in Desktop |
| Kaggle data terms | Raw files never committed; download script; attribution in the README |
| Tabular Editor 2 TMDL support changes between releases | The CI pins TE2 2.29.0 (GA TMDL, TOM 19.90) by checksum; fallback: store the model as `model.bim` for the CI check |
| Azure SQL free offer unavailable in the allowed region (happened) | Basic tier (2 GB, about $5 a month); the ERP holds under 50,000 rows ([ADR-011](../decisions/ADR-011-paid-f2-capacity.md)) |
| Weather API limits or outages | One call per city, 15 seconds apart, with retries; nothing is written unless every city succeeds; stored in `erp.weather_daily` |
| Scope creep | Cut in this order: Direct Lake variant → composite variant → field parameter → weather visuals |
